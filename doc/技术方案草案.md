项目名称：ClawWork 
文档类型：技术方案文档
版本：V1.0
适用阶段：MVP 立项与开发评审
客户端技术栈：React Native
Agent 控制平面：OpenClaw Gateway

---
2. 项目目标
本项目不是做一个“很多功能页的办公 App”，而是做一个：
用户通过文字 / 语音 / 文件把任务交出去，系统理解任务、调用 Agent、返回可交付结果，并支持连续改稿 的对话式办公产品。
MVP 重点验证 4 件事：
1. 用户愿不愿意通过对话发起办公任务
2. 用户愿不愿意在移动端把真实工作交给 Agent
3. 文档总结、邮件草拟、会议纪要、周报生成是否是高频首批任务
4. 用户是否认可“先给我一版”的价值

---
3. 技术目标
3.1 产品层目标
- 首页足够轻，打开就能交任务
- 文本、语音、文件都能作为任务入口
- 结果不是普通聊天，而是可交付成果
- 连续追问和改稿顺滑
- 历史记录按“任务”组织，而不是按消息组织
3.2 技术层目标
- React Native 一套代码覆盖 iOS / Android
- 客户端与业务后端清晰分层
- 通过 OpenClaw Gateway 统一承接会话与 agent 执行
- 支持流式结果返回
- 支持任务状态、结果版本、文件解析和历史恢复
- 后续可扩展更多 Agent 和更多消息渠道

---
4. 设计原则
4.1 客户端轻，服务端重
React Native 客户端负责体验和输入承接；任务理解、路由、文件处理、会话映射、结果管理尽量放在服务端。
4.2 OpenClaw 作为控制平面，不作为全部业务层
OpenClaw Gateway 适合作为会话与 agent 的控制平面。官方文档中，Gateway 在握手后提供 agent、send、status、health、node.list、node.describe、node.invoke 等方法，并通过事件流返回 agent 运行状态。
 但你自己的产品仍然需要独立的业务后端来管理：
- 用户
- 任务
- 文件
- 结果版本
- 计费
- 埋点
- 风控
4.3 任务是第一对象，不是消息
数据库、接口、页面结构都应以“任务”为中心组织，而不是单条消息。
4.4 先稳定，再智能
MVP 阶段先用清晰可控的任务路由和结构化输出，不追求一开始做复杂 Planner。

5. 总体架构
建议采用五层架构：
A. React Native 客户端层
负责：
- 登录
- 首页 / 对话页 / 结果页 / 历史页 / 设置页
- 文本输入
- 语音录制
- 文件选择和上传
- 流式结果展示
- 复制与继续追问
B. 业务后端层
负责：
- 用户体系
- Session 与 Task 管理
- 文件元数据
- 结果版本
- 配额 / 订阅
- 埋点 / 审计
- 风控
C. Task Router / Agent Adapter 层
负责：
- 任务识别
- 输出结构确定
- 会话映射
- 调用 OpenClaw Gateway
- 消费 Gateway 事件流
- 转为客户端可消费的任务流
D. OpenClaw Gateway 层
负责：
- WebSocket 控制面
- 会话状态
- agent 调用
- 节点状态与节点调用
- 事件分发
OpenClaw 官方说明里，Gateway 是单个长期运行的核心进程，控制平面客户端通过 WebSocket 与它通信，agent 响应是两阶段：先 accepted，再通过 event:"agent" 流式输出，最终返回 ok 或 error。
E. 数据与基础设施层
包括：
- PostgreSQL
- Redis
- 对象存储
- 文档解析服务
- 日志 / 监控 / 异常系统

6. 技术选型
6.1 客户端：React Native
选择原因
- 一套代码覆盖 iOS / Android
- 适合 MVP 快速迭代
- 对对话型产品足够胜任
- 团队若有 React/前端背景，开发效率高
- 便于快速接入输入框、文件上传、列表、卡片式结果页
推荐基础框架
建议使用 Expo + React Native 启动，除非你非常确定会在 MVP 一开始就依赖大量深度原生能力。
 React Native 官方当前也推荐以 Framework 方式开始项目，以便获得更完整的生产能力工具链。
客户端核心库建议
- 路由：Expo Router 或 React Navigation
- 状态管理：Zustand
- 服务端状态：TanStack Query
- 表单：React Hook Form
- 网络请求：fetch / axios
- 流式处理：EventSource polyfill 或 WebSocket
- 文件选择：expo-document-picker 或 react-native-document-picker
- 语音录制：expo-av 或 react-native-audio-recorder-player
- 本地缓存：MMKV
- 崩溃监控：Sentry

---
6.2 后端
推荐技术栈
建议使用：
- Node.js + NestJS 作为业务后端
- 独立的 OpenClaw Adapter Service 对接 Gateway
为什么这样拆
业务后端负责你自己的产品逻辑；Adapter 负责把业务任务转换成 OpenClaw 的会话和 agent 调用。这样能避免把业务层耦合进 Gateway。

8. 服务端架构
8.1 服务拆分建议
最少拆成 4 个服务：
1）API / BFF 服务
职责：
- 对客户端提供 REST API
- 鉴权
- 任务创建
- 历史查询
- 文件元数据管理
- 配额校验
2）Task Router 服务
职责：
- 识别任务类型
- 识别输出结构
- 识别语气 / 对象
- 决定发给哪个 Agent
3）OpenClaw Adapter 服务
职责：
- 与 Gateway 建立持久 WebSocket
- 发起 connect
- 调用 agent
- 订阅 event:"agent"
- 处理 runId、accepted、ok/error
- 将事件转成业务状态
4）File Parser Worker
职责：
- 解析 PDF / DOCX / TXT
- 文本清洗
- 分段切块
- 抽取纯文本或摘要

---
8.2 为什么需要 Adapter 层
不要让 App 或普通 API 服务直接裸连 OpenClaw Gateway。
原因：
1. 需要统一处理会话映射
2. 需要把 Gateway 协议转成业务接口
3. 需要做重连、超时、幂等、错误码翻译
4. 需要屏蔽 Gateway 细节给客户端
5. 后续方便替换模型或 Agent 策略
OpenClaw Gateway 文档明确要求客户端第一帧先发送 connect，之后才能调用其他方法；同时 agent 结果是事件流 + 最终总结的两阶段响应。Adapter 正好适合吸收这部分协议复杂度。

9. OpenClaw 接入方案
9.1 接入角色
OpenClaw 在本项目中承担：
- 会话控制平面
- Agent 运行入口
- 事件流来源
- 节点能力扩展入口
OpenClaw README 也明确写到 “The Gateway is just the control plane — the product is the assistant.” 这和你现在的产品形态非常匹配。

---
9.2 Gateway 通信方式
你的 Adapter 服务通过 WebSocket 接入 Gateway。
握手
第一帧发送：
- method: "connect"
常用方法
- status
- health
- agent
- node.list
- node.describe
- node.invoke
常用事件
- agent
- presence
- tick
- shutdown
这些都是 OpenClaw 官方网关手册列出的协议方法和事件。

---
9.3 Agent 调用流程
业务流程
1. 客户端创建任务
2. API 服务写入任务表
3. Task Router 判断任务类型
4. Adapter 根据 task_type + session_context 组织 OpenClaw agent 调用
5. Gateway 返回 accepted
6. Gateway 持续推送 event:"agent"
7. Adapter 转换为任务流式输出
8. 最终写入结果版本表
9. API 向客户端推送完成状态
会话映射
建议你自己的系统维护一层映射：
- app_session_id
- user_id
- task_id
- openclaw_agent_id
- openclaw_session_key
这样前端按“任务会话”理解，底层按 Gateway 会话运行。

12. 语音方案
12.1 MVP 推荐方案
React Native 客户端只负责：
- 录音
- 上传音频
- 展示转写文本
语音转写由服务端调用外部 ASR 完成。
为什么这样做
- MVP 重点不是实时语音通话
- 重点是“用语音发起办公任务”
- 录音后转写比实时流式更容易稳定落地
12.2 第二阶段可增强
- 边录边转写
- 实时语音输入
- 语音播报结果
- 真正的对讲式办公体验
OpenClaw README 提到它在 macOS/iOS/Android 上可 “speak and listen”，但你产品是否直接依赖它做完整语音链路，可以留到第二阶段再评估。

15. 流式通信方案
15.1 客户端到业务后端
建议：
- 普通接口走 HTTPS
- 任务流式结果走 SSE
为什么优先 SSE
- 比 WebSocket 更轻
- 对“服务端持续往下推结果”很合适
- React Native 接入成本可控
- 你的业务形态更像“任务进度流”，不是强双向聊天室
15.2 Adapter 到 Gateway
建议：
- 长连接 WebSocket
- 连接池或单实例持久连接
- 统一管理重连、心跳、错误处理
OpenClaw Gateway 本身就是围绕 WebSocket 请求 / 响应 / 事件模型设计的，所以 Adapter 用持久 WS 是最自然的接法。

17. 权限与安全
17.1 基础安全
- JWT 鉴权
- HTTPS 全链路
- 私有对象存储
- 上传文件白名单
- 服务端限流
17.2 数据安全
- 文件访问必须与 user_id 绑定
- 历史任务支持删除
- 任务日志脱敏
- 语音和文档做隐私标记
17.3 Gateway 侧安全
OpenClaw 文档提到可配置 Gateway token，并在 connect 期间带入；同时错误码里包括 INVALID_REQUEST、UNAVAILABLE、AGENT_TIMEOUT 等。你的 Adapter 层应该统一翻译这些底层错误，不直接暴露给 App。

21. 技术风险
21.1 React Native 流式体验复杂度
长文本流式渲染、任务状态、版本切换、文件上传状态同时存在，前端状态管理容易混乱。
21.2 会话映射风险
如果 App 的 task/session 和 OpenClaw session 没映射好，容易出现追问串上下文。
21.3 文档处理质量风险
文件解析质量直接影响最终结果质量。
21.4 Gateway 依赖风险
如果没有 Adapter 层缓冲，Gateway 的连接和协议复杂度会直接泄漏到业务层。
21.5 范围失控风险
一旦把“邮件发送”“工具调用”“多 Agent 编排”全部一起做，MVP 会失控。
