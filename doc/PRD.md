2. 项目概述
2.1 一句话定义
一个基于 OpenClaw 的对话式办公 Agent App，让白领只需要通过文字或语音“交代任务”，系统就能完成文档总结、邮件草拟、会议纪要、周报生成等事务性工作。
2.2 产品本质
这不是传统意义上的“办公工具集合”，也不是泛聊天机器人，而是一个：
以对话为入口、以 Agent 为执行核心、以结果交付为目标的移动办公代理产品。
2.3 为什么现在做
白领在日常工作中有大量“应该有人先做一版”的任务，但现实中没有这样的助理支持。与此同时，地铁、通勤、等车、开会前后等碎片时间很多，却缺少适合用一句话就能启动任务的产品。
2.4 为什么基于 OpenClaw
OpenClaw 官方定位是自托管 AI gateway，可连接多种聊天入口，并支持会话、路由、文档/音频输入、Web 控制界面与移动节点能力；这使它非常适合承载“对话即入口、Agent 负责任务执行”的产品形态。

---
3. 产品愿景与目标
3.1 产品愿景
让 AI 成为白领的对话式实习生。
3.2 核心目标
让用户在任何碎片场景中，通过一句话把工作交出去，并在最短时间内拿到可用初稿。
3.3 MVP 目标
验证以下假设：
1. 用户愿意通过自然语言而不是复杂功能页发起办公任务
2. 用户愿意在手机端把真实工作交给 AI 先处理
3. 文档总结、邮件草拟、纪要整理、周报生成是最高频的首批任务
4. 用户真正愿意付费的点，不是“AI 聪明”，而是“AI 能先把活做了”

---
4. 产品定位
4.1 定位描述
面向通勤白领与知识工作者的对话式办公 Agent。
4.2 差异化
与传统办公产品相比，本产品不是“用户学会功能”，而是“系统学会理解任务”。
4.3 与泛 AI 助手的区别
泛 AI 助手偏向问答和陪伴；本产品偏向工作交付。
 核心价值不是“回复”，而是“执行并产出结果”。

5. 用户与场景
5.1 目标用户
核心用户
- 互联网、运营、销售、咨询、市场、行政等知识工作者
- 高通勤、高会议密度用户
- 经常需要写文档、邮件、纪要、汇报的人
- 手机上处理工作频繁的人
用户特征
- 工作被会议和消息切得很碎
- 不缺判断力，缺时间和注意力
- 很多内容不需要自己从零写
- 愿意为效率和节省精力付费

---
5.2 用户画像
用户画像 A：通勤白领
岗位：运营经理
特点：每天地铁通勤 50 分钟，工作中经常需要总结文档、回邮件、写周报
痛点：手机打字慢，但脑子里知道要做什么
诉求：开口就能把任务交出去
用户画像 B：会议密集型员工
岗位：项目经理
特点：开会多，切换快，follow-up 特别多
痛点：知道该写纪要，但没空整理
诉求：系统帮忙把会议内容先整理成结构化结果
用户画像 C：轻管理者
岗位：团队负责人
特点：对外需要正式表达，对内需要发通知、对上需要汇报
痛点：很多表达都只是“需要先有一版”
诉求：AI 先写一版，自己最后确认

---
5.3 核心场景
场景一：地铁里处理文档
用户在通勤途中收到一份文档，说：
“帮我总结这份文档，提炼成 3 点，再给我一个适合发老板的版本。”
场景二：走路时草拟邮件
用户边走边说：
“帮我写一封跟进客户的邮件，礼貌催一下进度，不要太硬。”
场景三：会议后立刻整理纪要
用户上传会议记录后说：
“帮我整理成会议纪要，分成结论、待办、负责人。”
场景四：碎片时间生成周报
用户上传零散工作记录后说：
“根据这些内容，写一版本周周报，分成完成项、问题、下周计划。”
场景五：表达优化
用户说：
“把这段话改成适合发群通知的版本。”

6. 用户痛点
1. 很多事务性工作必须做，但不值得本人从零开始写
2. 碎片时间很多，但现有办公产品不适合碎片化操作
3. 手机上多工具切换复杂，输入成本高
4. 传统办公产品是“找功能”，不是“交任务”
5. 用户真正想要的是“能直接拿去用”的内容，不是长篇建议

---
7. 产品原则
7.1 对话优先
用户先说任务，而不是先找功能。
7.2 结果优先
系统先给交付物，再给解释。
7.3 轻交互优先
交互范式参考豆包这类产品的简洁对话入口、明显语音入口和轻量快捷标签，但不复制视觉，而是把它升级成更适合办公结果交付的体验。豆包官方/App Store 页面强调“打开就能问”“简单清爽的界面设计”“便捷而且准确的语音输入”“多轮对话”等特征。
7.4 连续上下文优先
用户应像和助理改稿一样连续推进任务，而不是频繁新建任务。OpenClaw 官方也明确把 Gateway 作为会话与路由的核心来源，并支持按智能体、工作区或发送者隔离会话。
7.5 Agent 执行优先
Agent 必须承担真实任务推进，而不是只负责聊天包装。

12. 详细功能需求
12.1 功能一：首页 / 会话入口页
目标
让用户在 3 秒内理解：这是一个可以“交任务”的地方。
功能
- 显示欢迎语和示例任务
- 支持文本、语音、文档上传
- 支持点击快捷标签直接发起任务
- 显示最近任务入口
- 显示最近使用文件
规则
- 不做复杂功能宫格
- 首页必须围绕“任务入口”设计
- 首次打开无需教程也能开始

---
12.2 功能二：任务型对话输入
目标
让用户用自然语言快速表达需求。
支持输入形式
- “帮我总结这份文档”
- “写一封客户跟进邮件”
- “改成老板能看的版本”
- “再短一点”
- “更正式一些”
要求
1. 默认不强制用户先选分类
2. 系统自动识别任务类型
3. 当识别不明确时，进行最少量澄清
4. 语音输入支持转写后发送
5. 上传文件后，系统应提示用户补充任务目标
异常处理
- 语音识别失败：提示重试或改文本
- 文件上传失败：提示重传
- 文件过大：提示压缩或截取

---
12.3 功能三：任务识别与路由
目标
把一句自然语言变成可执行任务。
识别维度
- 任务类型：总结 / 草拟 / 改写 / 纪要 / 周报
- 输出对象：老板 / 客户 / 群 / 同事
- 输出风格：正式 / 简洁 / 礼貌 / 强硬
- 输出结构：邮件 / 列表 / 纪要 / 周报
- 上下文关系：新任务 / 基于上一版改写
路由逻辑
- 文档总结 → 文档 Agent
- 写邮件 → 邮件 Agent
- 会议纪要 → 纪要 Agent
- 周报 → 汇报 Agent
- 含糊任务 → 通用办公 Agent
要求
- 路由过程不暴露给用户
- 用户只感知“我说了，系统懂了”

---
12.4 功能四：结果生成与交付
目标
给用户一个可直接拿去用的结果。
输出规则
- 先给结果
- 少给冗长解释
- 输出结构清晰
- 优先可复制、可发送、可继续修改
任务类型输出要求
文档总结
输出：
- 3-5 条重点
- 可选一版“给老板/给同事”的改写结果
邮件草拟
输出：
- 邮件标题建议
- 邮件正文
- 可选不同语气版本
会议纪要
输出：
- 会议主题
- 核心结论
- 待办事项
- 负责人（如可识别）
周报 / 汇报
输出：
- 本周完成
- 问题与风险
- 下周计划
操作
- 一键复制
- 一键重写
- 风格切换
- 继续追问
- 保存到任务历史

---
12.5 功能五：连续改稿与追问
目标
让用户像在和助理改稿一样连续推进。
典型追问
- 再短一点
- 更正式一点
- 改成发老板的版本
- 改成适合群通知
- 加一句催进度但礼貌一点
- 提炼成 3 条
要求
- 保留当前任务上下文
- 追问默认基于上一版结果
- 支持至少连续 5 轮改写
- 支持查看上一版历史

---
12.6 功能六：历史任务页
目标
让用户回到“那封邮件”“那个纪要”“上次的总结”，而不是只看到消息记录。
展示内容
- 任务标题
- 任务类型
- 更新时间
- 结果摘要
- 继续任务入口
功能
- 搜索
- 筛选
- 再次编辑
- 复制结果
- 删除任务
要求
- 按任务组织，而不是按单条消息组织
- 优先展示最近使用内容

---
12.7 功能七：设置页
内容
- 账号信息
- 会员信息
- 默认输出风格
- 默认结果长度
- 默认语言
- 隐私与数据说明
- 反馈入口
偏好项
- 默认正式程度
- 默认输出结构
- 常用对象偏好（老板 / 客户 / 同事）

14. 核心交互流程
14.1 文档总结流程
1. 用户进入首页
2. 上传文档
3. 输入：“帮我总结成 3 点，再给我发老板版”
4. 系统识别“总结 + 改写”
5. 输出摘要和老板版
6. 用户追问：“再短一点”
7. 系统继续优化
14.2 邮件草拟流程
1. 用户输入：“写一封客户跟进邮件，礼貌催进度”
2. 系统生成标题和正文
3. 用户追问：“更正式一些”
4. 系统改写
5. 用户复制结果
14.3 会议纪要流程
1. 用户上传会议记录
2. 输入：“整理成会议纪要，按结论、待办、负责人输出”
3. 系统输出结构化纪要
4. 用户复制到群或文档

16. 非功能需求
性能
- 首页打开时间尽量控制在 2 秒内
- 短文本任务应快速返回
- 文档任务需有明确处理中提示
可用性
- 对话入口必须简单
- 语音入口必须明显
- 关键操作可单手完成
- 结果卡片阅读清晰
稳定性
- 弱网场景下有清晰反馈
- 上传失败可重试
- 会话中断后可恢复最近任务
隐私与安全
- 用户上传文档应有清晰隐私提示
- 历史任务支持删除
- 敏感办公内容不得默认公开展示

19. 风险与挑战
1. 结果质量风险
 如果用户觉得还得自己大改，就不会持续使用。
2. 语音场景噪音风险
 通勤场景对语音识别不友好。
3. 任务识别风险
 自然语言自由度高，误解会直接影响信任。
4. 弱网风险
 地铁、通勤环境网络波动明显。
5. 范围失控风险
 Agent 产品很容易做成大而全，MVP 必须克制。

---
20. MVP 验收标准
满足以下条件即可认为 MVP 可上线测试：
1. 用户可通过一句自然语言发起任务
2. 系统稳定支持 4 类核心任务：
  - 文档总结
  - 邮件草拟
  - 会议纪要
  - 周报生成
3. 用户可连续追问改稿
4. 用户可复制并实际使用结果
5. 至少 70% 内测用户认为：
  - 比自己从零写省时间
  - 结果可作为第一版使用
  - 愿意再次使用
